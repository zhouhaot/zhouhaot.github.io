# zhou 产品与架构设计规格

- 日期：2026-07-18
- 状态：已获方向批准，待书面规格复核
- 原项目：VOID.DEV 个人博客
- 新产品名：zhou

## 1. 设计目标

将现有的静态个人博客模板重新设计为面向创业团队、中小企业和潜在合作伙伴的 AI 应用开发者作品集。

产品通过可运行项目、开源代码、技术文章和 AI 工作流实验建立技术可信度，首要转化是引导访客访问 GitHub 和查看代表作品，次要转化是产生企业 AI 转型合作或求职沟通。

本次重构不是对现有赛博朋克主题的换肤，而是重新定义品牌、信息架构、内容模型、前端架构和发布流程。

## 2. 已确认的产品决策

- 品牌名固定为 `zhou`，作为不绑定真实姓名的个人技术符号。
- 不公开姓名、头像、住址、电话等个人身份信息。
- 用户后续提供的简历只用于理解经历；公开内容必须经过脱敏和逐项确认。
- 对外身份为“AI 应用开发者”。
- 核心价值是理解前沿 AI 工作流，并将模型、Agent、知识库和自动化流程转化为企业可使用的应用。
- 目标用户优先级：创业团队与中小企业客户，其次是招聘方和技术负责人。
- 第一阶段只提供中文。
- 技术栈不受现有原生 HTML/CSS/JavaScript 约束。
- 现有 VOID.DEV 视觉体系全部废弃，不保留赛博朋克品牌表达。
- 当前样例身份、履历、文章、项目和链接均不视为真实内容。
- 没有证据支持的客户、成果数据和商业案例不得展示。

## 3. 品牌表达

### 3.1 品牌主张

第一阶段品牌口号：

> 探索技术边界，让 AI 真正进入业务。

辅助说明：

> 从 AI 工作流、智能体到企业应用，构建可验证、可交付、可持续演进的解决方案。

### 3.2 品牌语气

- 专业、直接、技术可信。
- 用工程证据说明能力，避免空泛的 AI 热词。
- 明确区分已完成项目、实验原型、研究笔记和未来设想。
- 不使用夸大式企业转型承诺。

## 4. 用户与核心任务

### 4.1 主要用户

创业团队负责人、中小企业决策者和潜在合作伙伴。他们需要快速判断：

1. zhou 是否理解实际业务，而不只是模型 API。
2. 是否具备把 AI 工作流做成稳定应用的工程能力。
3. 是否有可验证的代码、原型和思考过程。
4. 是否值得进一步联系或邀请参与项目。

### 4.2 次要用户

招聘方和技术负责人。他们需要快速判断：

1. 技术深度与学习能力。
2. 产品意识和完整交付能力。
3. 项目中的真实个人贡献。
4. GitHub 代码和工程质量。

### 4.3 核心转化

- 主转化：访问 GitHub、查看代表仓库或运行中的 Demo。
- 次转化：发起合作咨询或求职沟通。
- 第一阶段不以注册、订阅、评论或付费为转化目标。

## 5. 信息架构

### 5.1 一级导航

- 首页 `/`
- 作品 `/work`
- AI 实验室 `/lab`
- 技术文章 `/notes`
- 关于 zhou `/about`
- GitHub（站外链接）

### 5.2 首页结构

1. **Hero**：品牌、定位、主张、GitHub 主按钮、合作咨询次按钮。
2. **精选作品**：最多 3 个能证明完整交付能力的项目。
3. **AI 能力地图**：Agent、RAG、工作流自动化、模型接入、评估与部署。
4. **AI 实验室**：小型、可运行、可复现的技术原型。
5. **企业 AI 落地方法**：发现问题、验证场景、制作原型、集成业务、评估迭代。
6. **技术文章**：展示判断力、研究能力和持续输出。
7. **开源与 GitHub**：代表仓库、贡献方式和代码证据。
8. **当前状态**：正在求职，同时接受合适的 AI 应用合作。
9. **联系区**：GitHub 为主要入口，保留低摩擦的合作联系方式。

### 5.3 内容为空时的处理

第一版不得用虚构客户案例填充页面。正式作品不足时：

- 精选作品区展示经过整理的个人项目或可运行原型。
- 没有足够作品时隐藏多余卡位，不展示“敬请期待”卡片。
- AI 实验室承担早期能力证明职责。
- 客户评价、合作品牌、量化商业成果等模块暂不出现。

## 6. 内容模型

### 6.1 Work（作品）

必填字段：

- `title`
- `slug`
- `summary`
- `problem`
- `role`
- `solution`
- `stack`
- `contributions`
- `status`
- `publishedAt`
- `featured`

可选字段：

- `repositoryUrl`
- `demoUrl`
- `architecture`
- `screenshots`
- `outcomes`
- `limitations`
- `nextSteps`

作品详情的固定叙事顺序为：问题、约束、职责、方案、架构、关键实现、结果、局限与复盘。

### 6.2 Lab（AI 实验）

用于展示范围较小但可验证的技术探索：

- `title`
- `slug`
- `hypothesis`
- `workflow`
- `modelOrTools`
- `result`
- `evaluation`
- `repositoryUrl`
- `demoUrl`
- `status`
- `publishedAt`

实验必须标注状态，例如 `prototype`、`validated`、`archived`，不得包装成正式商业项目。

### 6.3 Note（技术文章）

- `title`
- `slug`
- `summary`
- `tags`
- `publishedAt`
- `updatedAt`
- `draft`
- `content`

文章支持代码、架构图、表格、引用、目录和相关文章。

### 6.4 Profile（匿名职业资料）

- 公开定位
- 能力领域
- 经脱敏的经历摘要
- 当前状态
- GitHub 地址
- 公开联系方式

不存储或发布真实姓名、头像、详细地址、私人电话和未确认的公司信息。

## 7. 视觉与交互设计

### 7.1 视觉方向

采用“技术编辑部 + AI 实验室”风格：

- 深灰或近黑中性色背景，不采用霓虹赛博朋克。
- 单一高识别度强调色，具体颜色由 OpenDesign 方案确定。
- 强调字阶、网格、留白和内容层次。
- 视觉素材优先使用真实产品界面、运行结果、架构图和代码。
- 品牌标识采用文字标识、抽象符号或生成式图形，不使用人物头像。

### 7.2 动效原则

- 动效用于状态反馈、内容进入和页面关系表达。
- 不保留持续运行的粒子背景、自定义鼠标光晕和普遍性 3D 倾斜。
- 支持 `prefers-reduced-motion`，关闭非必要运动。
- 动效不得阻塞阅读或降低移动端性能。

### 7.3 可访问性

- 目标为 WCAG 2.2 AA 的相关要求。
- 所有交互使用原生语义元素或完整补足语义。
- 完整支持键盘操作、可见焦点、跳过导航和正确标题层级。
- 图片必须有符合语境的替代文本。
- 表单错误必须同时提供文字说明，不能只依赖颜色。

### 7.4 OpenDesign 交付约束

原型至少包含：

- 首页、作品列表与详情、实验室列表与详情、文章列表与详情、关于页、404。
- 桌面和移动端关键视图。
- 导航、按钮、卡片、标签、代码块、筛选器和联系区的状态。
- 加载、空数据、错误和长内容状态。
- 字体、颜色、间距、栅格、断点、图片比例和动效说明。
- 每个版位与内容字段的映射。

开发允许在不改变设计意图的前提下补全响应式、可访问性和异常状态。

## 8. 技术架构

### 8.1 第一阶段技术栈

- Astro
- TypeScript 严格模式
- Astro Content Collections
- Markdown/MDX 内容
- CSS Custom Properties 设计令牌
- 少量 Astro Islands 承载确有必要的交互
- Vitest 用于纯逻辑和内容校验
- Playwright 用于关键页面和转化路径
- GitHub Actions 用于构建、测试和部署

### 8.2 渲染策略

- 首页、作品、实验和文章全部在构建期生成独立 HTML。
- 第一阶段不依赖运行时数据库。
- 仅搜索、筛选、复制代码等局部能力使用客户端 JavaScript。
- RSS、sitemap、canonical、结构化数据和 OG 元数据由构建流程生成。

### 8.3 内容事实源

第一阶段以 Git 仓库中的 Markdown/MDX 和资源文件为唯一事实源：

```text
内容文件 / 图片
  -> Content Collections schema 校验
  -> Astro 构建静态页面
  -> 生成 sitemap / RSS / SEO 元数据
  -> 自动测试
  -> 静态部署
```

现有 `/admin` 不迁移到第一阶段生产系统。它只写当前浏览器 localStorage，无法构成真实发布闭环，应在新系统上线时移除，而不是继续对外提供。

### 8.4 后续后端触发条件

只有出现以下真实需求时才引入托管数据库或 CMS：

- 需要跨设备编辑。
- 非开发人员需要发布内容。
- 需要草稿、审核、定时发布和版本回滚。
- 需要媒体库、客户咨询数据或多人权限。
- 内容更新频率使 Git 工作流成为明确阻碍。

届时优先评估 Supabase 或 Headless CMS，但不在第一阶段预建空后台。

## 9. 组件边界

建议组件分层：

```text
layouts/
  BaseLayout
  ContentLayout
  DetailLayout

components/primitives/
  Button
  Link
  Tag
  Icon
  Surface

components/navigation/
  SiteHeader
  MobileNavigation
  Footer

components/content/
  WorkCard
  LabCard
  NoteCard
  ContentMeta
  Prose
  CodeBlock

components/sections/
  Hero
  FeaturedWork
  CapabilityMap
  DeliveryMethod
  GitHubProof
  CurrentStatus
  ContactCTA
```

页面负责组合组件和获取内容，组件不直接读取全局存储。每个组件通过明确 props 接收数据，视觉变量由统一设计令牌控制。

## 10. 数据流与错误处理

### 10.1 构建期

- Content Collections schema 拒绝缺少必填字段、无效日期和重复 slug。
- 外链字段只允许 `https:`，邮件只允许 `mailto:`。
- 草稿在生产构建中排除。
- 引用不存在的图片或关联内容时构建失败。

### 10.2 运行时

- 静态内容不依赖 API，避免首屏数据请求失败。
- GitHub 数据若采用实时请求，必须有静态快照和失败降级，不能导致页面主体不可用。
- 无筛选结果显示明确空状态。
- 未知路由进入自定义 404。
- 第三方 Demo 不可访问时仍保留项目说明与源码链接。

## 11. SEO、性能与隐私

### 11.1 SEO

- 使用无 Hash 的稳定 URL。
- 每页生成唯一标题、描述、canonical 和 OG 信息。
- 作品使用 `CreativeWork`，文章使用 `Article`，关于页使用 `ProfilePage`，其 `mainEntity` 为以公开化名 `zhou` 表达的 `Person`。
- 自动生成 sitemap 和 RSS。
- 旧 Hash URL 不作为可延续的索引地址；新站上线时为旧首页保留迁移说明，并在最终部署平台支持重定向规则时，为非 Hash 的历史路径配置永久重定向。

### 11.2 性能目标

- Lighthouse Performance 目标不低于 90。
- Accessibility、Best Practices 和 SEO 目标不低于 95。
- 非必要页面不加载交互框架运行时。
- 图片生成响应式尺寸，并优先输出现代格式。
- 字体数量和字重受预算约束。

### 11.3 隐私

- 第一阶段不引入广告追踪。
- 如需统计，优先选择低 Cookie 或无 Cookie 方案。
- 公开前对简历和经历执行隐私扫描。
- 联系入口第一阶段优先使用公开邮箱或 GitHub，不收集不必要的个人数据。

## 12. 测试与验收

### 12.1 自动化测试

- 内容 schema 和 URL 安全校验。
- sitemap、RSS、canonical 和结构化数据生成测试。
- 关键组件单元测试。
- Playwright 覆盖首页、作品详情、实验详情、文章详情、GitHub 主转化和 404。
- 使用 `axe-core` 进行自动可访问性检查。
- 桌面与移动端关键页面视觉回归。

### 12.2 人工验收

- Chrome、Edge、Firefox、Safari 最近两个主要版本。
- 常见桌面、平板和移动视口。
- 仅键盘浏览。
- 系统减少动态效果模式。
- 弱网及第三方 GitHub/Demo 不可用场景。
- 所有公开内容完成事实核验和隐私确认。

## 13. 迁移策略

1. 保留当前仓库和 Git 历史。
2. 在实施前建立内容清单，将真实内容与示例内容分离。
3. 新建 Astro 架构和统一设计系统。
4. 仅迁移经过确认的文章、作品和配置。
5. 使用 OpenDesign 原型实现新页面。
6. 完成 SEO、测试和部署流水线。
7. 新站验收通过后移除旧 SPA、主题引擎和 `/admin`。

旧系统中的 `Core.parseMarkdown`、转义测试和内容结构可作为迁移参考，但不直接继承 localStorage 数据优先级、Hash 路由、运行时主题注入或前端伪认证。

## 14. 第一阶段范围

包含：

- 品牌与设计系统。
- 响应式首页。
- 作品列表与详情。
- AI 实验室列表与详情。
- 技术文章列表与详情。
- 匿名化关于页面。
- GitHub 与合作入口。
- RSS、sitemap、SEO 元数据和 OG 基础设施。
- 内容迁移与 schema 校验。
- 自动化测试和部署。

不包含：

- 在线管理后台。
- 数据库和用户账户。
- 多人协作、评论、邮件订阅和客户门户。
- 多语言。
- 未经证实的商业成果和客户案例。

## 15. 开始实施前的输入

- 经脱敏处理后可公开的简历信息。
- GitHub 地址和计划展示的仓库。
- 首批作品、实验或原型的真实资料。
- OpenDesign 原型及组件/响应式说明。
- 最终公开联系方式。

这些输入可以分批提供。缺失时可搭建内容结构和组件，但不得用虚构材料替代最终公开内容。

## 16. 验收结论

当以下条件同时满足时，第一阶段完成：

1. 访客能在首页快速理解 zhou 的 AI 应用开发定位。
2. 作品与实验提供可验证的代码、Demo 或技术证据。
3. GitHub 主转化在桌面和移动端清晰可用。
4. 所有公开身份和经历内容经过脱敏确认。
5. 页面拥有独立 URL，SEO、RSS、sitemap 和 OG 信息可正确生成。
6. 关键测试、可访问性和性能门槛通过。
7. 旧 localStorage CMS 和前端伪认证不再作为生产能力存在。
